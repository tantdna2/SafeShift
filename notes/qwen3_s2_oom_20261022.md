## Observations and uncertainty

The supplied rerun has 941 planned rows: 717 SUCCESS, 1 TECHNICAL_ERROR and 223
NOT_ATTEMPTED. Native-call markers cover ordinals 0–717; one model load. The error
is at zero-based ordinal 717, sample
`coal_conveyor-Level02-SuspendedRail-002595-001`, image hash
`c82dd1b1c3386b67a0372c1b9ea98de68b60cdc586436dfecd3c4c061cc9e8f5`.

Its call shapes are `input_ids=attention_mask=[1,4581]`,
`pixel_values=[16128,1536]`, `image_grid_thw=[1,3]`. Ordinals **129, 521, 570,
652** have exactly these shapes and each completed 10 generation steps. This is
not equality of input content, grid *values*, input dtype/device, allocation
history or workspace demand. Those latter properties were not all captured.

The failed journal contains call, processor-list and stopping observations and
only `OutOfMemoryError` as its exception type; no completed native/trace/step
summary. Native generation was entered. Its exact failing operation is unknown:
there is no stage/traceback separating vision, decoder prefill/decode, native
return and the operations before the first native artifact write. A missing
artifact cannot identify that allocation. The worker's outer status `RETURNED`
means the lifecycle returned with `inference_complete=false`; it is not 941-image
success.

## Image-to-generate and object lifetime

1. `Backend.generate` reads staged image bytes and verifies their SHA-256. The
   Qwen path clears `rope_deltas` and `_cache`. `prepare_input` decodes a single
   image in memory, converts RGB, invokes the native chat template/processor and
   `.to(model.device)`, closes the PIL image, and rejects supplied past KV state.
   There is no custom resize or replacement preprocessing here. `model.device`
   and Accelerate dispatch must be observed, not inferred from CPU embeddings.
2. The runner/model stay loaded once across the unit. Placement fixes visual,
   head, norm and decoder layers 21–35 on GPU1, layers 0–20 on GPU0, embeddings on
   CPU; FP16, NONE quantization, SDPA and `expandable_segments:True` are enforced.
   The two devices have independent capacity limits; free capacity on one is
   not automatically available to an allocation on the other.
3. An isolated generation config is deep-copied. Effective kwargs set batch-one
   greedy generation, maximum 32 new tokens, and all three capture flags. Stored
   checkpoint `do_sample=true` defaults are overridden by the recorded kwargs;
   they are not evidence of effective sampling.
4. In pinned Transformers 4.57.1, `generate` initializes a per-call dynamic cache,
   updates it through prefill/decode and returns it with the output. The greedy
   loop copies the last-token logits to FP32, retains requested raw/processed
   step vectors, and deletes each intermediate forward output before the next
   step. With an empty processor list, raw and processed scores can share a
   tensor; two tuples do not prove two physical copies. Native support already
   sets `logits_to_keep=1`; retaining output logits does not imply retaining a
   `[4581,vocab]` matrix. Source:
   [pinned generation implementation](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/generation/utils.py),
   [pinned processor list](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/generation/logits_process.py),
   [pinned Qwen3 model](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py).
   These source observations are not GPU profiling of the supplied run.
5. The saved success tensor layout is `[1,151936]`, FP32 on CUDA1. Arithmetic:
   one raw tuple at 32 steps contains 19,447,808 bytes (18.55 MiB); at 10 steps,
   6,077,440 bytes (5.80 MiB). Counting separate raw and score storage gives a
   conservative 37.09 MiB bound for those vectors alone, excluding tuples,
   native head temporaries, KV cache, vision/decoder activations, dispatch copies
   and allocator workspace. This is a size calculation, not an observed peak or
   a reason to discard required evidence. Likewise 24,772,608 pixel elements
   would occupy 94.5 MiB in FP32 or 47.25 MiB in FP16; call shapes do not prove
   their actual dtype.
6. `persist_torch` retains the returned output/cache while writing native IDs
   and all raw/processed summaries before decode. `summarize_tensor` allocates a
   temporary FP64 vocabulary vector for reductions. The sample is sealed before
   CPU parsing/HNLO replay. Successful return clears model call state and
   `self.cap`; local inputs/output/prepared values leave the adapter frame. The
   engine stores JSON results, not tensors. `self.calls` stores integer ordinals.
   The backend's class patches retain the loaded lifecycle, not a history of
   native outputs. Accelerator/native-library lifetimes remain unmeasured.
7. On failure, success-path cleanup is skipped; the engine records/seals the
   error and stops with no retry. A traceback can transiently retain a failing
   frame. `self.cap` may retain the failed journal until shutdown; it does not
   contain GPU tensors. This cannot explain 717 *earlier* successful calls by
   itself and is not proof of the initiating OOM. Final cleanup/refactoring is
   not offered as an OOM repair without a reproduction.

## Hypotheses, not findings of causality

| Hypothesis | Evidence consistent with it | Missing discriminating evidence |
| --- | --- | --- |
| Transient peak in vision/prefill/decode/persistence | Large shape, lifetime peaks near capacity, lower final live allocation | Stage markers, per-stage/per-device allocation/free counters, native forward events, OOM message/allocation size |
| Live tensor accumulation across calls | Failure occurs late | Per-sample live-allocation trend, native-hook/cache ownership; source/CPU ownership test shows no adapter output history, not absence of native leaks |
| Allocator fragmentation/history | Many varying allocations and high reserved memory | OOM-time active/inactive split stats, allocator backend/config confirmation, bounded allocation history; reserved alone is insufficient |
| Placement capacity/dispatch limit on one T4 | Explicit independent device limits; vision/head/layers share GPU1 | Actual failed device/op and contemporaneous usage on both devices; aggregate maxima do not identify the failing GPU |

Confidence is high in the supplied rerun's failure location/coverage and the
missing observability, low in any specific root-cause attribution. No justified
runtime change follows. No `empty_cache`, GC loop, logits removal, precision,
resolution, quantization, placement, prompt, decoding or sample-order change was
implemented. A later repair requires new technical evidence and independent
review; an execution-condition change needs a separate research decision.

## Measurement design for a future separately authorized run — NOT IMPLEMENTED/RUN

The present CLI cannot start this run. A subsequent implementation/audit must
add a separate entrypoint/source lock/authority/audit contract; it must not route
the 224-row plan through V4's 941-row worker or weaken V4's gates.

- Observe after load, before/after image preparation, immediately before/after
  native generate, before/after persistence/clear, and at the next sample boundary.
  Use scalar per-device allocated/reserved/peak values, CUDA free/total,
  `memory_stats` active/inactive-split bytes, allocation-retry/OOM counters and
  allocator backend/config. Record unavailable fields and observer errors as
  such; do not report them as zero. Separate lifetime and interval peaks if peak
  stats are reset; preserve earlier observations first.
- Inside native generation, use bounded pre/post hooks around vision and model
  forward to distinguish prefill from decoding step, with no tensor retention
  or returned-value edits. Record actual input dtype/device, grid values and
  lengths; never emit image pixels, label-bearing IDs/paths or GT into the
  worker. Bind every event to new run/attempt, recovery ordinal, stage and clock.
- On OOM, durably retain the original exception class/module/message, cause
  chain and relative module/function/line stack **without locals**, then collect
  best-effort scalar stats on **both** GPUs. Preserve any original message naming
  the device and failed byte count; `current_device` is not proof. No retry,
  reload, cache flush or error rescue. Retain partial raw observations and seal
  failure evidence before finalization; observer failure must not hide OOM.
- Keep device-wide 10-second sampling explicitly PARTIAL_SAMPLED. Do not claim
  it captures a sub-second peak. Bounded allocator history/snapshots require
  pinning the PyTorch private API, new storage/retention review and measured
  overhead before enabling. No synchronized profiling by default: added CUDA
  synchronization can change timing/peak behavior and attribution of async
  errors. Any such profiling is a separately declared diagnostic condition.

Interpretation criteria: rising *live* allocation at equivalent cleared sample
boundaries motivates ownership investigation; stable boundaries with a local
spike motivates peak/placement investigation; inactive-split/OOM allocation
history may support fragmentation. None alone establishes causality. A fresh
process starting with the failing sample changes allocation history and cannot
reproduce all 717 prior samples without additional exposure and authority.
